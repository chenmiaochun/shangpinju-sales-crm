# 尚品居销售软件正式上线与长期更新手册

## 1. 正式架构

- 员工入口：GitHub Pages 固定网址，统一使用 `#` 路由，员工收藏同一个地址。
- 业务服务：Render 上的 Node.js API，负责登录、权限、审计和数据库读写。
- 正式数据库：Render 持久磁盘 `/var/data` 内的 SQLite 数据库。
- 代码与数据分离：发布前端或后端新版本不得覆盖 `/var/data`。
- 浏览器缓存只用于临时显示和离线容错，正式数据以服务端数据库为准。

## 2. 首次上线必须完成

1. 在 Render 使用仓库根目录的 `render.yaml` 创建 `shangpinju-sales-api`。
2. 确认已挂载 1 GB 持久磁盘到 `/var/data`。
3. 设置强密码环境变量 `SALES_ADMIN_PASSWORD`，不得写入仓库或群聊。
4. 打开 `https://<实际服务地址>/api/health`，确认返回成功。
5. 在 GitHub 仓库 Actions Variables 设置：
   - `SALES_STATIC_DEMO=false`
   - `SALES_API_URL=https://<实际服务地址>`
6. 发布 `main` 分支，等待前端和后端均部署成功。
7. 用管理员账号登录，按岗位创建员工账号并配置最小权限。

在以上七项完成前，不允许录入真实客户资料。当前静态演示数据不能迁移为正式共享数据源。

## 3. 正式启用验收

负责人：老板负责最终批准；技术执行人负责证据留存；陈婉珊负责业务数据核对。

验收标准：

- 两台不同设备、两个员工账号可以同时登录。
- A 设备新增客户后，B 设备刷新可看到；反向新增也成立。
- 同一客户并发补充不同记录，不丢失新记录。
- 普通员工无法进入管理员功能，不能恢复数据库或修改成员权限。
- 管理员可以下载 JSON 备份，备份不含密码哈希和登录会话。
- 在隔离测试环境完成一次“备份—修改—恢复”演练。
- 手机端完成新增线索、填写活动字段、跟进和查询各一次。
- 连续试用 2 个工作日无数据丢失后，老板书面确认转为正式使用。

验收证据：测试账号、时间、设备、测试记录编号、截图、备份文件名和异常处理结果。

## 4. 日常备份

- 每个工作日闭店前：管理员下载一次 JSON 备份。
- 每周：把当周最后一份备份复制到第二个受控位置。
- 每次发版前：必须下载一份发版前备份。
- 每月：在隔离环境抽查一次备份可恢复性。
- 备份文件含客户经营资料，只能由老板指定人员保存，不得发到公开群或个人网盘。

建议文件名：`sales-backup-YYYY-MM-DD-HHmm-before-release.json`。

## 5. 长期更新流程

所有更新分成三类：

### A. 仅页面或字段展示调整

1. 在独立开发分支修改。
2. 运行全部自动测试和生产构建。
3. 用测试数据验收电脑端、手机端。
4. 合并到 `main` 自动发布。

### B. 新增业务字段或流程

除 A 类步骤外，还必须：

- 保留旧字段，新增字段先允许为空。
- 对旧记录提供默认值或兼容读取。
- 导入、导出、备份、恢复和权限同步更新。
- 发版后抽查旧客户、旧订单和新记录各一条。

### C. 数据库结构、权限或退款合同相关调整

- 发版前必须由老板审批。
- 必须先备份，并在副本数据库完成迁移演练。
- 写明回滚方案、影响范围和验收人。
- 禁止直接在正式库试错或批量改写历史记录。

## 6. 回滚原则

- 页面或程序故障：回滚代码版本，不删除或替换正式数据库。
- 错误数据写入：先停止相关操作、下载现场备份，再按审计记录确定修复范围。
- 只有老板批准且已验证备份时，才可执行正式库恢复。
- 禁止用旧备份直接覆盖正式库来处理普通页面故障。

## 7. 账号与权限

- 每人独立账号，不共用管理员账号。
- 离职或调岗当天停用或调整权限。
- 价格、退款、预算、活动政策和成员权限仍由老板审批。
- 管理员密码只保存在批准的密码管理位置，定期更换。
- 每月核对成员清单、角色和最近操作审计。

## 8. 当前上线闸门

只有同时满足以下条件，才通知内容员工录入真实线索：

- Render 正式 API 已上线并通过健康检查。
- 持久磁盘确认存在。
- GitHub Pages 已设置为非静态模式并指向实际 API。
- 管理员和首批员工账号已建立。
- 两设备共享、权限、并发、备份恢复验收全部通过。

任何一项未通过，页面只能用于演示和培训，不得作为公司正式客户数据库。
