## 0. 背景与目标

当前系统的商品是**一行一个**的扁平结构（`ProductCatalogItem`：一个商品一条记录，一个价格、一个库存数），销售开单、库存、采购都基于它。老板需要一个更贴近定制家具行业的**多级产品主数据体系**：

- 从「组件库」出发，**手工精选**出要卖的「成品（单品）」和「套餐」
- 产品库成为全系统的**中心主数据**，销售 / 库存 / 采购 / 售后 / 经营分析都引用它
- **权限分层**：员工只看到成品（单品/套餐），老板/采购/财务能看到组件层价格与成本

目标不是简单加功能，而是把商品体系升级为系统地基（Master Data）。

## 1. 业务概念与层级（已与老板确认）

```
第1层  大类 ProductCategory     餐桌类 / 沙发类 …
第2层  主件 ProductComponent    餐台面 / 餐台脚 / 转盘 …（每个主件有自己的规格维度）
第3层  规格维度 ComponentSpecDim 餐台面=尺寸+材质（2维）；餐台脚=尺寸+款式+材质（3维）
第4层  最小单位 SkuUnit          主件×规格取值 的组合，如「餐台面/1.8m/黑胡桃」→ 挂价格/成本/库存
第5层  单品 ConfigProduct        老板手工精选组合，如「1.8m 黑胡桃圆餐桌」
第6层  套餐 ProductPackage       单品组合，如「餐厅套系 = 餐桌×1 + 餐椅×4/6可选 + 餐边柜×1」
```

**要点：**
- 每个主件的规格维度**可以不一样**（台面 2 维、台脚 3 维），不是所有主件共用一套规格。
- 最小单位（第 4 层）才真正挂价格、成本、库存；上面全是组合层。
- 单品是「主件组合」出来的虚拟层，不直接存库存；套餐是「单品组合」的再上一层，可跨主件甚至跨大类。

## 2. 关键业务规则（已确认，必须遵守）

### 2.1 不自动生成全组合（最重要）
- 组件库可以很大，但**单品由老板手工精选创建**，系统**绝不自动铺开**所有规格组合（避免"21 个规格组合 × 主件 = 几百张餐桌"的检索灾难）。
- 员工永远只看到老板精选出来的成品。

### 2.2 价格公式
```
单品标准价 = Σ(主件价格 × 数量) + 增减价（增减价可正/可负/可 0）
套餐价     = Σ(单品标准价 × 数量) + 套餐增减价
```
- 增减价由老板创建单品/套餐时设置，用于"不能写死、要适当调价"的场景，主件价不动。
- 开单时仍可手工改单价 / 给折扣（保留现有 `OrderItem.unitPrice` / `discountAmount` 能力）。

### 2.3 编码系统自动生成
- 主件：短代码（拼音缩写，如 餐台面=`CTM`、餐台脚=`CTJ`、转盘=`ZP`，建主件时设一次）。
- 最小单位 SKU：`主件代码-规格值代码`，如 `CTM-1.8M-HZW`、`CTJ-1.8M-ZJ-HZW`。
- 单品：`SP-大类码-序号`，如 `SP-CT-001`；套餐：`TC-序号`。
- 原则：**唯一（重复自动加序号）、可读（看码能猜规格）、可扩展（新增规格维度不影响老编码）**。

### 2.4 库存与开单扣减
- 库存挂在**最小单位**上。
- 开单选单品 → 系统按配置模板**自动展开成最小单位明细**（如 台面×1+台脚×1+转盘×1）→ 各扣对应最小单位库存。
- 含「定制生产」主件的单品 → **不扣现货库存**，自动生成「生产需求单」，走现有 采购/生产 流程，到货后入库再计库存。
- 保留直接开「最小单位」配件单的能力（如单独买一块台面）。

### 2.5 组合规则（要简单，不建复杂规则表）
- 约束全部写在单品配置模板里：每个主件可设置「锁定某规格值」或「开放某几个规格值」。
- 例「1.8m 黑胡桃圆餐桌」= 台面(尺寸锁定 1.8m，材质开放 黑胡桃/白蜡木) + 台脚(尺寸锁定 1.8m，款式开放 直脚/弯脚) + 转盘(可选)。
- 由此"方台面配圆桌脚"等非法组合天然不会出现。

### 2.6 权限分层（员工 vs 老板）
| 角色 | 成品(单品/套餐) | 组件层 / 价格 / 成本 |
|---|---|---|
| 销售 / 售后 / 运营（员工） | ✅ 看得到：名称、售价、可用库存、上下架状态 | ❌ 不可见 |
| 店长 / 采购 / 财务（老板侧） | ✅ | ✅ 组件售价 + 成本 + 库存 |

- 开单时员工仍可选规格（尺寸/材质），但**只显示该配置的成品总价，不展示组件分项价与成本**。
- 复用现有权限体系（`inventory.manage`、`cost.view` 等），在 `src/features/team/access.ts` 中补充组件层可见性权限。

## 3. 数据结构设计（新增到 `src/types.ts`）

> 产品资料范围：**B 完整电子手册版**（老板已选定）——除 品类/主件/规格/SKU/单品/套餐 外，数据模型含"媒体与资料"（多图、详情卖点、尺寸/材质/颜色图、安装保养说明、质检标准、手册附件、适用空间/风格/系列、上下架与展示排序）。UI 可后做，但结构在 Phase 1 一并建好，避免二次迁移。

```ts
// 媒体文件（图片 / 附件统一）
export interface MediaFile {
  id: string
  name: string
  type: string          // image/png、application/pdf…
  url: string           // 上传后的公网地址（经服务端 uploads 上传，勿用 base64 塞状态）
  size?: number
}

// 产品媒体资料（挂在单品 / 套餐上）
export interface ProductMedia {
  images: MediaFile[]          // 多张主图/产品图（第一张为主图）
  dimensionImages?: MediaFile[] // 尺寸图
  materialImages?: MediaFile[]  // 材质图
  colorImages?: MediaFile[]     // 颜色图
  installationDoc?: MediaFile[] // 安装说明
  careDoc?: MediaFile[]         // 保养说明
  manualFiles?: MediaFile[]     // 产品手册 / 附件（PDF 等）
  qualityStandard?: string      // 质检标准（含水率、色差、结构标准）
}
```

```ts
// 大类
export interface ProductCategory {
  id: string
  name: string          // 餐桌类 / 沙发类
  code: string          // 大类代码，如 CT（餐桌）/ SF（沙发）
  sort: number
}

// 规格维度定义（挂在主件下，每个主件自己的）
export interface ComponentSpecDim {
  id: string
  name: string          // 尺寸 / 款式 / 材质
  values: string[]      // 尺寸: ['1.6m','1.8m']；材质: ['白蜡木','黑胡桃']
}

// 主件
export interface ProductComponent {
  id: string
  categoryId: string    // 属于哪个大类
  code: string          // 短码，如 CTM / CTJ / ZP
  name: string          // 餐台面 / 餐台脚 / 转盘
  sort: number
  specDims: ComponentSpecDim[]
}

// 最小单位 SKU（主件 × 规格取值）
export interface SkuUnit {
  id: string
  componentId: string
  sku: string           // 自动生成：CTM-1.8M-HZW
  specValues: Record<string, string>  // { 尺寸:'1.8m', 材质:'黑胡桃' }
  unitPrice: number     // 售价
  costPrice: number     // 成本
  supplyType: SupplyType // 现货/展厅样品/外采产品/定制生产
  availableStock: number
  reservedStock: number
  safetyStock: number
  supplier?: string
  image?: string        // 可选：材质/颜色特写图
  status: '上架' | '下架'
}

// 单品（可配置商品 = 主件配置模板 + 增减价 + 媒体资料）
export interface ConfigProduct {
  id: string
  categoryId: string
  name: string          // 1.8m 黑胡桃圆餐桌
  code: string          // 自动生成：SP-CT-001
  description?: string  // 详情 / 卖点描述
  style?: string        // 风格：意式极简 / 新中式…
  series?: string       // 所属系列：五福沙发系列…
  applicableSpace?: string[]  // 适用空间：客厅 / 餐厅 / 卧室…
  sortOrder: number     // 展示排序（越小越靠前）
  media?: ProductMedia  // 多图 / 尺寸图 / 材质图 / 安装保养 / 手册 / 质检标准
  components: ConfigProductComponent[]  // 组合模板
  adjustPrice: number   // 增减价（可正可负可 0）
  status: '上架' | '下架'
}

export interface ConfigProductComponent {
  componentId: string
  quantity: number      // 数量（餐脚 1 套、台面 1）
  optional: boolean     // 是否可选（转盘）
  locked?: Record<string, string>        // 锁定规格值 { 尺寸:'1.8m' }
  allowed?: Record<string, string[]>     // 开放规格值 { 材质:['黑胡桃','白蜡木'] }（不填=全部开放）
}

// 套餐（可配置组合）
export interface ProductPackage {
  id: string
  name: string          // 餐厅套系
  code: string          // 自动生成：TC-001
  description?: string
  sortOrder: number     // 展示排序
  media?: ProductMedia
  items: PackageItem[]
  adjustPrice: number   // 套餐增减价
  status: '上架' | '下架'
}

export interface PackageItem {
  productId: string     // 引用单品
  quantity: number      // 默认数量（餐桌×1）
  quantityOptions?: number[]  // 可选数量（餐椅 [4,6]）
  optional?: boolean
}
```

**价格计算（前端工具函数）**
```
configProductPrice(product, pick): number
  = Σ over components ( 选中 SkuUnit.unitPrice × quantity ) + product.adjustPrice

packagePrice(pkg, picks): number
  = Σ over items ( configProductPrice(item.product, itemPick) × item.quantity ) + pkg.adjustPrice
```

**库存展开（开单扣减用）**
```
expandConfigProduct(product): SkuUnit[]   // 把单品按模板展开成"已选中"的最小单位明细
```
- 全现货：每个 SkuUnit.availableStock -= quantity
- 含定制生产：不扣库存，转 SupplyDemand 生产需求

**数据持久化说明（已核实，含服务端，非纯前端）**
- 数据流：前端启动后从 `GET /api/state` 加载远端状态；状态变更通过 `PUT /api/state` 把**全量状态**保存到服务端 SQLite 的 `app_state` 表（单行 id=1）；浏览器 localStorage（key=`shangpinju.customer-followup.v1`）只是本地缓存，**服务端是最终数据源**。
- 服务端**无需新增数据库表**（状态是整体 JSON 存在 `app_state` 单行），新增集合会随全量状态自动携带。
- 但新增集合必须同时处理 4 条路径，不能按纯前端实施：
  1. `RemoteSalesState`（`salesApi.ts`）加入新集合 → 走 `/api/state` 加载与保存
  2. `SalesState` / `loadState`（`SalesDataContext.tsx`）缺省 `[]` → 老数据自然兼容
  3. 服务端 `CONCURRENT_RECORD_KEYS`（`server/database.mjs`）加入新集合 → 启用按记录并发合并（当前 `products` 也不在其中，属整数组覆盖；新集合建议加入以获得按记录合并）
  4. 备份 / 恢复：`app_state` 全量 JSON 自动携带新集合；`PUT /api/state` 校验与恢复路径需回归验证

**媒体 / 附件存储约定（B 版电子手册）**
- 图片与附件走服务端现有 uploads 上传能力（`server/index.mjs` 已配置 `uploadDir`），**存 URL 而非 base64**，避免 `app_state` 单行 JSON 因大量图片暴涨。
- `MediaFile.url` 存上传后的公网地址；状态里只存元数据 + URL，图片本体在服务端 uploads 目录（随备份恢复走 uploadDir）。

## 7. 风险与注意

1. **数据双端存储（localStorage 缓存 + 服务端 `app_state` 全量状态）**：新增集合必须同时兼容 前端 `loadState` 缺省值、`/api/state` 加载保存、服务端 `CONCURRENT_RECORD_KEYS` 并发合并、备份恢复 四类路径，**绝不能丢老数据**。
2. **权限是核心**：组件成本/增减价绝不能对员工可见；开单也只显示成品总价。
3. **不做全组合自动生成**：任何"自动铺开规格组合"的实现方向都是错误的。
4. **分阶段推进**：每阶段独立验收、不影响老板日常使用；不要一步到位。
